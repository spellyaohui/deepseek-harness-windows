## Manual acceptance after installation

Fully exit and restart the app. In a new conversation, create a new ad-hoc Team with
member names/roles only, no Profile and no explicit model or reasoning override. Use
a saved temporary default different from the captain. Inspect actual exported child
request configuration rather than trusting a member's self-description.

Repeat with a configured Profile, then explicit model/reasoning arguments. Both must
keep their own policies. Changing the live defaults must not reroute an existing Team.
Superpowers remains available in the native skill catalog and explicit `/` invocation.

Real paid-model execution, NSIS installation, long-running usage and second-machine
acceptance are left to the user. The source/tests/package evidence below does not
establish those manual acceptance levels.

## Implementation decisions and costs if wrong

1. Canonical main, no new worktree: explicit user choice; uncommitted changes stay
   here until separately authorized integration.
2. Review working diffs with complete new-file inventories instead of commits:
   local-test-only boundary; omission from the inventory would need re-review.
3. Parallelize only disjoint core/Superpowers modules: separate ownership; shared
   dependency setup had to remain controller-owned to avoid races.
4. Complete the actual v0.1.23 source migration, not relabel the route-only patch:
   upstream feature requirement; this required a longer integration/review cycle.
5. Retain strict V2 instead of automatic historical coercion: established user
   constraint; malformed old state remains rejected rather than silently repaired.
6. Model the actual builder's metadata/dev-file exclusions during validation:
   observed production output; excluded development/docs are not byte-compared,
   while runtime scripts/assets/versions remain strict and independently closed.
